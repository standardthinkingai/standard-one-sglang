# MI325X (gfx942) bring-up, 2026-10-06

One AMD Instinct MI325X (256 GB HBM3E, ROCm 7.1 host), 20 vCPU, 157 GB RAM.
The GPU was shared with two unrelated vLLM servers (a 27B model each, about
160 GB VRAM and part of the compute) during every run below, so the
throughput numbers are a floor, not the MI325X's ceiling. Nothing of theirs
was touched.

Model: `StandardOne-8B` v2.2 (`ac495d1c221297f0ae951941eff27bcf58b5ce52`),
GPU readout `standardone-8B-v22-gpu-readout.npz`, label scheme `upper`, the
production flags of the MI350X host (`launch-decision.sh`, profile `gfx942`).

## Image

`Dockerfile.decision` with
`BASE_IMAGE=lmsysorg/sglang-rocm:v0.5.20-rocm720-mi30x-20260929` (the gfx942
build of the same SGLang release the MI350X image uses; sglang-kernel 0.4.7,
same aiter and triton commits). Fork `668d985318`, adapter `398c067e31`.
Build time about 3 minutes once the 93 GB base image is pulled. **No source
change was needed for gfx942**: the fork's Python package and the adapter
import and serve unchanged.

## Correctness

- Relaxed canary against the MI350X v2.2 golden (112 questions, recorded
  from the production image on gfx950): 112/112 same answer, max |Δp| 0.022,
  two passes identical. Every triton start was identical to every other.
- Cross-host parity set (4,705 requests: the three text eval sets 3,210,
  1,275 image-view pairs from the image validation set, 20 wide choices with
  27-255 options, 200 option variants: return_logprobs, assistant_prefix,
  permutations) answered by this host in 124 s at concurrency 16; the same
  file is answered by the MI350X branch image for the per-question comparison
  (`tools/xparity.py diff`). Result: see "Cross-host parity" below.

## gfx942 optimization candidates

Each candidate ran as a fresh container, canary-checked against the golden
first (aiter attention was corrupt on about half of the starts on gfx950, so
every aiter start here is classified), then the same text and image load.

Correctness (canary vs the MI350X golden, 112 questions, two passes):

| candidate | starts | canary | max abs Δp | note |
|---|---|---|---|---|
| triton (baseline, `SGLANG_USE_AITER=0`) | 3/3 healthy | 112/112, two passes identical | 0.022 | 42-46 s to healthy |
| `--attention-backend aiter` | 3/3 healthy | 112/112, identical | 0.022 | **no corrupt start on gfx942** (gfx950: 6/10 corrupt); 200-250 s to healthy (JIT builds two `mha_batch_prefill` variants, ~80 s each; the vision encoder's varlen kernel builds on the first image request) |

| both (`SGLANG_USE_AITER=1` + aiter attention) | 1/1 healthy | 112/112, identical | 0.066 | |
| prefill CUDA graph (breakable, dense buckets to 16384, `MEM_MB=40000`) | 1/1 healthy | 112/112, identical | 0.022 | 106 s to healthy (capture) |
| `HIP_FORCE_DEV_KERNARG=1 HSA_NO_SCRATCH_RECLAIM=1` | 1/1 healthy | 112/112, identical | 0.022 | no effect: the base image already sets both |

Initial throughput: the first baseline and the first aiter-attention run were taken
while the other tenants' two vLLM servers were idle (triton 66.2 / 2.30 /
16.2 req/s for small-4q c16 / big-64q c16 / image c16; aiter attention 62.9
/ 2.47 / 16.2, i.e. the same within noise). From 06:05 UTC a third tenant
container trained at 100 % GFX for the rest of the session, which cut every
later measurement by 4-7x (e.g. triton small-4q c16 9-15 req/s), so the
aiter-ops and prefill-graph throughput rows are not comparable and are not
reported. `chain-quiet.sh` subsequently re-ran six configurations back to
back from 08:57 UTC. Its initial low-utilization trigger does not establish
that the GPU remained dedicated throughout the run; the GPU was still
shared. The following results supersede the initial "no aiter ops gain"
conclusion.

| configuration | 4q c1 p50 ms | 4q c16 req/s | 64q c1 p50 ms | 64q c16 req/s |
|---|---:|---:|---:|---:|
| triton | 36.85 | 68.27 | 429.55 | 2.45 |
| triton repeat | 37.15 | 68.10 | 429.60 | 2.48 |
| aiter attention only | 36.00 | 63.30 | 420.25 | 2.50 |
| aiter ops only | 33.90 | 74.79 | 393.00 | 2.69 |
| aiter ops + attention | 31.30 | 79.20 | 384.80 | 2.72 |
| prefill graph | 38.60 | 49.29 | 441.95 | 2.25 |

Each c1 row has only 12 measured requests after two warmups. The larger
1q/4q sequential sweep below uses 100 measured requests per case. The
quiet-run image c1 figures for aiter ops include cold vision/JIT time and
must not be treated as steady-state image latency. The subsequent `x-*`
runs warm images through the full parity set before their image loads.

Decision for the `gfx942` profile: **triton attention, aiter ops off**, the
same as gfx950. aiter attention is stable on gfx942 but was not faster by
itself, costs 3-4 minutes of JIT at every container start
unless the kernels are baked into the image, and keeping one attention
backend across both AMD families keeps the canary goldens interchangeable.
aiter ops improve these measured latencies and throughput, but move the
canary probabilities by up to 0.05-0.07 and reduce full-set agreement with
the MI350X reference (see the follow-up results below). They remain an
experimental opt-in, not the default. Agreement with another engine is
not labeled-task accuracy; these comparisons do not establish which answer
is correct.

## Stability soak (triton, shared GPU at 100 % GFX from another tenant)

15 minutes of text (8 concurrent clients cycling 600 eval-set requests) and
image (8 clients, distinct 512 px images, 4 questions) load at once, canary
before and after: 2,716 text and about 2,100 image requests, 0 errors, 0
engine log faults, both canaries 112/112 with max |Δp| 0.022 and two
passes identical. The same text request re-answered under a different
batch composition moved by at most 0.017 (BF16 batch effects, inside the
canary tolerance).

The full-set follow-up started at 09:19 UTC after the quiet-run sweep.
All three runs completed 4,705 requests / 6,125 questions, every response
HTTP 200, with no status or token-usage mismatch against the MI350X
branch-image reference (`arch-8B-branch-20261006T053359Z`).

|---|---:|---:|---:|---:|---:|
| triton (`x-triton-20261006T093403Z`) | 6,035 | 98.53% | 0.00084 | 0.0342 | 0.1473 |
| aiter ops (`x-aiter-ops-20261006T092750Z`) | 5,986 | 97.73% | 0.01043 | 0.0797 | 0.1846 |

On the same MI325X, triton vs aiter ops agreed on 97.70% of questions;
triton vs aiter ops + attention agreed on 97.50%. Hence the numerical
change is observable without comparing different GPU families.

**One-question requests can be below 20 ms on MI325X.** The earlier
30-40 ms comparison was four questions, not one. For the 52-token case,
c8 gives most of c16's throughput with roughly half its p50 latency;
this is a useful observed balance if the aiter numerical tradeoff is
acceptable. For the 406-token four-question case, c8 to c16 gains only
2.8% throughput while nearly doubling p50, so c4/c8 is the better latency
tradeoff. Choose the external concurrency for the workload and latency
budget; it is not the engine's `MAX_RUNNING_REQUESTS` value.

The old MI350X four-question 23.55 ms p50 used model revision
`36d7999c…`; current v2.2 (`ac495d1c…`) measured 38.20-40.05 ms on the
same 406-410-token shape. Those historical runs do not isolate a GPU
speed difference or prove that model weights caused the timing change.

At this snapshot the 15-minute aiter text+image soak is still running
(`soak-aiter-both-20261006T093944Z`); no completion or stability claim is
made for it. The planned triton 1q sweep and max-running 64/128 experiments
were canceled before starting at the owner's request to commit the
currently measured values. The existing triton default is retained.
